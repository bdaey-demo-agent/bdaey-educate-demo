# قرار معماري: نموذج الـ Multi-Tenancy في بدائي Educate

التاريخ: 2026-11-22
الحالة: مقترح للمراجعة — لم يُنفَّذ أي كود multi-tenant بعد

## السؤال

إزاي نبيع المنصة لأكاديميات ومعلمين كثر؟ في مسارين:

- **المسار أ: نسخة منفصلة لكل أكاديمية (Database + Container per tenant)**
- **المسار ب: قاعدة واحدة مشتركة بعمود TenantId (Shared schema)**

## الوضع الحالي (نقطة الانطلاق)

- المنتج مكتمل كـ single-tenant: 28 controller و21 entity وصفر `TenantId` في `ApplicationDbContext`.
- الـ frontend جاهز لفكرة الـ subdomains أصلًا: `config.ts` بيحوّل `{academy}.lms.bdaey.com` للـ API الخاص بالأكاديمية تلقائيًا.
- الـ white-label اتجهز (commit d3e1ec4): الاسم والشعار والألوان بيتظبطوا من env vars لكل نسخة.
- المدفوعات (Kashier) بتتظبط من config لكل deployment — يعني كل أكاديمية تقدر تشتغل بحساب تاجر Kashier **بتاعها هي**، والفلوس تدخل حسابها مباشرة.
- في مشروع منفصل عندنا (`Bdaey_SaaS_Enterprise`) فيه محرك provisioning شغال بالفعل: بيعمل سيرفر Fly.io + قاعدة Neon مخصصة لكل عميل في ~٦٠ ثانية، مع ربط دومين وSSL واشتراكات وتجديد تلقائي وأرشفة النسخ المنتهية.

## المقارنة

| المعيار | أ: نسخة منفصلة | ب: TenantId مشترك |
|---|---|---|
| جاهزية الكود الحالي | عالية: الـ frontend والـ config والـ white-label متجهزين له بالفعل | منخفضة: لازم TenantId في كل الـ 21 entity وكل الاستعلامات |
| عزل بيانات العملاء | كامل (قاعدة منفصلة) — نقطة بيع قوية للأكاديميات | منطقي فقط؛ أي bug في فلتر واحد يسرّب بيانات أكاديمية لأكاديمية تانية |
| مدفوعات كل أكاديمية بحسابها | طبيعي (env config لكل نسخة) | يحتاج إعادة تصميم مسار Kashier بالكامل (multi-merchant) |
| الترقيات والتحديثات | أصعب: N نسخة محتاجة deploy/migrations | deploy واحد للكل |
| التكلفة التشغيلية | ~سعر machine + قاعدة لكل أكاديمية (تتسعّر في الاشتراك) | أرخص على الورق، لكن التعقيد يروح للكود |
| تعديل قاعدة البيانات | كل نسخة على إيقاعها، والـ migrations موجودة وتشتغل تلقائي عند الإقلاع | migration واحد كبير وخطر على كل العملاء |
| إعادة استخدام كود Enterprise | المحور كله جاهز (provisioning + اشتراكات + دومينات) | لا ينطبق |

## التوصية: المسار أ (نسخة منفصلة لكل أكاديمية)

الأسباب:

1. **أقصر طريق للفلوس.** الهدف مش بناء SaaS مثالي، الهدف بيع اشتراكات الشهر الجاي. المسار أ محتاج شغل تكامل (provisioning) أكتر منه شغل إعادة كتابة — ومحرك الـ provisioning جاهز ومُجرّب في Enterprise.
2. **عزل البيانات ميزة بيع** في سوق الأكاديميات الدينية (بيانات طلاب وأولياء أمور)، مش رفاهية تقنية.
3. **حساب Kashier لكل أكاديمية** بيحل سؤال "الفلوس بتروح فين" من غير ما نبني multi-merchant billing.
4. **صفر مخاطرة على المنتج الشغال.** المسار ب يلمس كل سطر في قاعدة البيانات وكل استعلام — أعلى احتمال كسر في المشروع كله.

### متى نرجع نفكر في المسار ب؟

لو عدد الأكاديميات عدّى ~٣٠-٥٠ نسخة وتكلفة التشغيل/الترقية بقت عبء واضح، ساعتها دمج المخازن الصغيرة في قاعدة مشتركة يبقى قرار اقتصادي مبني على أرقام فعلية، مش تخمين.

## خطوات التنفيذ المقترحة (ترتيب تقريبي)

1. **Tenant registry خفيف** (في بوابة Enterprise أو service صغير): سجل لكل أكاديمية — subdomain، رابط قاعدة البيانات، حالة الاشتراك، نسخة الـ brand env.
2. **نقل محرك الـ provisioning** من Enterprise (تعميم الكود على "تطبيق = بدائي Educate" بدل ERP): إنشاء machine + قاعدة + دومين + تشغيل migrations.
3. **اشتراكات وفوترة**: إعادة استخدام نموذج الاشتراك/التجديد التلقائي من Enterprise، مع Kashier invoices للتحصيل.
4. **بوابة مالك المنصة**: إنشاء/إيقاف/أرشفة أكاديمية، ومتابعة حالة الاشتراكات (موجودة مبادئها في super-admin بتاع Enterprise).
5. **قالب brand لكل أكاديمية**: شاشة ترفع الشعار والاسم والألوان وتولّد الـ env vars تلقائيًا (الأساس اتجهز في item 3).

## مخاطر وملاحظات

- ترقية N نسخة تحتاج انضباط: الـ CI/CD لازم يعمل rolling deploys، وإلا هننسى نسخ قديمة. (الـ watchdog pattern في Enterprise بيعالج ده جزئيًا.)
- كل نسخة ليها JWT key وKashier credentials خاصة — إدارة الـ secrets تفضل في fly secrets لكل app، ممنوع تتخزن في git.
- النسخ المجانية/التجريبية تتشارك موارد (auto-stop machines) عشان التكلفة.
